# ZaZa SaaS tenancy architecture (Phase 10C)

ZaZa Employee Monitor is becoming a commercial multi-tenant SaaS, hosted on
Google Cloud (project `zaza-employee-monitor`, region `asia-south1`).

**Status:** this phase is the **architecture and local foundation only**.
- (At the time of 10C, no Google Cloud resource existed. Since 10E, the core
  infrastructure and the control database exist; see CLOUD_SQL_PRODUCTION.md.)
- No customer data is in Google Cloud.
- The running sync API and dashboard still serve one organization per
  database. The tenancy code is not wired into request handling yet.

Code is in `deskmate/zaza_server/tenancy/`, tests in
`tests/zaza_agent/test_tenancy.py` and `test_tenancy_postgres.py`.

**Phase 10D** added the production connectivity on top of this design (§10,
§12, §16): Cloud SQL socket configuration, the bounded tenant connection
manager, `tenant-migrate`, the provisioning boundary, `check-config
--cloud-run` and the Terraform definition. Details are in
[CLOUD_SQL_PRODUCTION.md](CLOUD_SQL_PRODUCTION.md). The infrastructure itself
was created later, in 10E.

## 1. Control plane vs. tenant data plane

```
                       ┌──────────────────────────── zaza_control (one database) ───┐
                       │ organizations            users (SaaS logins)                │
                       │ organization_memberships tenant_databases                   │
                       │ control_audit_logs                                          │
                       │ — no employees, devices, activity; no secrets —             │
                       └───────────────┬────────────────────────────────────────────┘
                                       │ organization_id → database_name (server-generated)
              ┌────────────────────────┼─────────────────────────┐
              ▼                        ▼                         ▼
   zaza_t_<random A> (tenant A)   zaza_t_<random B> (tenant B)   zaza_t_<random C> …
   employees, devices, device_tokens, work_sessions, activity_periods, idle_periods,
   work_schedules, daily/weekly/monthly_summaries, application_usage_daily, audit_logs,
   manager_users, manager_sessions   ← the existing schema 0001-0004, unchanged
```

- **Control plane**: one database for the whole service. It knows *who the
  customers are*, *who may administer them*, and *where each customer's data
  lives*. It never stores employee activity.
- **Tenant data plane**: one database **per organization**. Each holds that
  organization's data in exactly today's schema. The schema is the tenant
  template: migrations `0001_initial` … `0004_manager_dashboard_auth`. There
  is no `organization_id` in it; the database itself is the boundary.

## 2. Why database-per-tenant

ZaZa stores sensitive employee activity and attendance records. With one
shared database and an `organization_id` column on every table, a single
missing `WHERE organization_id = …` exposes every customer's employees. With
one database per tenant:

- A query can only see the database it is connected to. A programming
  mistake in normal tenant code cannot read another company's rows.
- Identifiers stay simple and local: two customers can both have employee
  `employee-1` and device `device-1` (proven in the local test).
- **Per-customer operations become possible:**
  - backup and restore of one customer;
  - export or deletion of one customer when a contract ends;
  - suspension of one customer;
  - a later move to a dedicated database server or region.
- Schema migrations roll out tenant by tenant and can be paused per tenant.

**Costs we accept:**
- more databases to migrate and monitor, and more connections (§16);
- cross-customer analytics need a deliberate, separate design (§13).

Row-level security in one shared database was rejected as the *default*:
it is a valid second line of defence, but one bad role or `BYPASSRLS`
setting undoes it.

## 3. Organization model

`organizations`: one customer company (e.g. "Zaza Studio", "ABC School",
"Acme Call Center").

| Column | Rule |
|---|---|
| `organization_id` | UUID, generated by the server, **immutable** (trigger) — the real identity |
| `slug` | normalized lower-case `a-z0-9` + inner hyphens, 3–63, unique, not reserved (`admin`, `api`, …). A URL/display handle — **never an authorization decision on its own** |
| `display_name` | 1–200 printable characters |
| `status` | `ACTIVE` · `SUSPENDED` · `CLOSED` |
| `default_timezone` | IANA name |
| `created_at`, `updated_at` | `TIMESTAMPTZ` (UTC); `updated_at` maintained by trigger |

There is no subscription or payment state here (§18).

## 4. Users vs. employees

| | **Control-plane user** (`users`) | **Tenant employee** (`employees` in a tenant DB) |
|---|---|---|
| Who | a person who logs in to the ZaZa SaaS (owner, admin, manager, viewer of a customer) | a person whose computer is monitored |
| Where | control database, once per person | each tenant database, per organization |
| Identity | `user_id` (UUID), unique normalized email | `employee_id` (text, unique within that tenant only) |
| Grants | nothing by itself; access comes only from memberships | nothing in the SaaS |

One person may manage several organizations: one `users` row, several
`organization_memberships`. User accounts are **not** copied into tenant
databases. There are no passwords or SSO fields yet: that comes in the SaaS
authentication phase, with no temporary password storage in the meantime.

The existing tenant tables `manager_users` / `manager_sessions` (migration
0004) are the **current single-organization dashboard login**. They stay
untouched. The control-plane user/session model will supersede them in the
SaaS authentication phase, which will also define how they are migrated or
removed.

## 5. SaaS RBAC

`organization_memberships (organization_id, user_id, role, status)`, with
one row per user per organization:

| Role | Meaning |
|---|---|
| `OWNER` | highest customer-level authority (organization settings, owners/admins) |
| `ADMIN` | organization configuration, employees, managers |
| `MANAGER` | operational dashboard access (later: limited to a team scope) |
| `VIEWER` | read-only reporting |

**`employees.role` (`EMPLOYEE`/`MANAGER`/`ADMIN`) is NOT a SaaS role.**
- It is a business classification of a monitored employee inside one
  tenant.
- No code maps it to a membership role. The database constraint allows only
  the four SaaS roles. An employee classified `ADMIN` gets no SaaS access
  (tested).
- `organization_memberships.role` is the only source of SaaS permissions.

## 6. Tenant database directory

`tenant_databases`: `organization_id` → its database. It is **one-to-one**:
the primary key is `organization_id`, and `database_name` is unique.

| Column | Rule |
|---|---|
| `organization_id` | FK, immutable |
| `database_name` | `zaza_t_` + 26 random base32 characters (128 bits), **generated by the server**. Never derived from a customer name, slug or request. Immutable. The database check, the domain validator and every use agree on the exact pattern, so `postgres`, `template1`, the control DB, quoting, spaces and connection strings are rejected |
| `region` | e.g. `asia-south1`; immutable (a move is a new database) |
| `status` | `PROVISIONING` · `READY` · `SUSPENDED` · `ERROR`. `READY` requires a `schema_revision` |
| `schema_revision` | the tenant migration head the database is at |

**No password, host, user, connection string or Secret Manager content is
stored here.** Connection details come from server configuration only
(§7, §16).

## 7. TenantContext

`TenantContext` (in `tenancy/context.py`) is the resolved, authorized
"working for organization X, in database Y" value:
- `organization_id`, `slug`;
- `database`, a validated `TenantDatabaseDescriptor`;
- `kind`: `MEMBER`, `DEVICE` or `JOB`;
- `role` and `user_id`, for member contexts only.

- **Only the resolver can issue one.** The constructor needs a module-private
  issuer key, and no other module imports it (tested).
- **It is immutable:** no setters, no `dataclasses.replace`, copies return
  the same object, and pickling is refused. Changing the slug can't move a
  context to another organization.
- **It is checked when built:** the descriptor must belong to the same
  organization and be `READY`.
- **The only way from a context to a connection** is
  `tenant_database_settings(base, context)`. Host, port, user, password, TLS
  and pool settings come from the **server's** `DatabaseSettings`; only the
  validated `database_name` changes. Nothing accepts a URL or connection
  string from a request.

## 8. Agent (device) tenant resolution

```
Authorization: Bearer zzd_…   +   X-ZaZa-Device-Id: device-1
        │
        ▼  hash the token (SHA-256)
control-plane credential router  ──►  organization_id   (unknown → 401)
        │                              (a client-claimed organization that differs → refused,
        ▼                               the claimed tenant's database is never opened)
TenantResolver: organization ACTIVE?  tenant database READY?   (else → refused)
        │
        ▼  TenantContext(kind=DEVICE)
open THAT tenant database → existing device authentication there
   (token hash exists, belongs to device-1, token ACTIVE, device ACTIVE)
        │
        ▼
sync is processed inside that tenant only
```

**The organization always comes from the credential, never from the
request.** "Client says organization = B" plus a valid token of A never
reaches B (tested: B's database is not even opened). The token is also
verified inside the routed tenant, so a router mistake can't authenticate a
device against the wrong tenant: the hash simply isn't there (proven in the
PostgreSQL test).

The high-entropy `zzd_` token design stays. The router is an interface
(`DeviceCredentialRouter`) in this phase. Its future implementation is a
control-plane index of credential hashes (or a non-secret routing prefix in
new tokens), written at enrollment (§17).

## 9. Manager (dashboard) tenant resolution

```
authenticated SaaS session (server-side) → user_id
        │
        ▼  user ACTIVE?
membership(organization_id, user_id) ACTIVE?     ← the organization the user picked
        │                                          (a slug in the URL is only a handle)
        ▼  organization ACTIVE?  tenant database READY?
TenantContext(kind=MEMBER, role=membership role)
        │
        ▼
dashboard queries that tenant database only
```

A membership in A never authorizes B (tested both ways). Unknown, suspended
or closed organizations, non-READY databases, disabled users and disabled
memberships produce **no** context. The error is the same generic
`TenantAccessDenied` in every case, so callers can't probe which
organizations exist.

## 10. Provisioning lifecycle (future automation; proven locally)

```
create organization (control)          organization.create            ACTIVE
assign tenant database                 tenant_database.assign         PROVISIONING   (name generated)
create the database (Cloud SQL, 10D)   —
apply tenant migrations 0001 → head    —
mark READY + schema_revision           tenant_database.status_change  READY
```

Failures leave the tenant in `PROVISIONING` or `ERROR`, which the resolver
never routes to. The local proof runs exactly this sequence against
disposable PostgreSQL.

**Phase 10D:** the sequence is code: `tenancy/provisioning.py`
(`TenantProvisioner`, `PostgresDatabaseCreator`). It also closes the new
database to PUBLIC and grants only the runtime role CONNECT plus DML. It is
not exposed by any CLI or HTTP route; Phase 10E/10F runs it with the
privileged migrator identity.

## 11. Control-plane migrations

- **A separate Alembic chain:** `deskmate/zaza_server/tenancy/control/migrations/`.
  Revision ids are `c0001_…` (branch label `control`), and the version table
  is `zaza_control_version`. The tenant chain uses `alembic_version` and
  `0001`…`0004`.
- **Head:** `c0001_control_plane`.
- **What it enforces:** named constraints for statuses, roles, slug, email,
  database name and region patterns, uniqueness and foreign keys
  (`ON DELETE RESTRICT`); `TIMESTAMPTZ` everywhere; immutable-identity
  triggers; append-only audit.
- **Run explicitly only:**
  `python -m deskmate.zaza_server control-migrate` (`--sql` prints the DDL
  without a database) and `control-db-status`. They use `ZAZA_CONTROL_DB_*`
  settings. A name is required, and it may not be a tenant name or the
  activity database. **Never at web start-up**: the Cloud Run entrypoint
  only serves.
- **Cross-guards:** the control chain refuses a database that holds tenant
  tables, and the tenant runner refuses a database that holds control
  tables.

## 12. Tenant migration lifecycle

- The tenant chain (`0001`…`0004`) is unchanged; a test pins the file
  hashes. A future tenant migration (`0005_…`) is applied **tenant by
  tenant**: list tenants, migrate one, record its `schema_revision`, move
  on.
- **Rollout:**
  - `serve` keeps refusing a tenant whose schema is not at the head the code
    needs (existing behaviour);
  - the rollout must deploy migrations **before** code that needs them, and
    keep code compatible with the previous revision during the rollout;
  - a failed tenant is marked `ERROR` and is not routed to; it does not
    block the others.
- No tenant migration is ever run at web start-up.
- **Phase 10D:** `python -m deskmate.zaza_server tenant-migrate
  --organization ID | --all-ready [--continue-on-error]` implements this
  (`tenancy/tenant_migrations.py`):
  - names come from the control directory only;
  - tenants run sequentially and each is reported;
  - a failure marks that tenant `ERROR`;
  - the control database is refused.

## 13. Reporting and scheduled jobs are per tenant

Every job runs with **one explicit TenantContext**:

```
control plane: list ACTIVE organizations with READY databases (ids only)
  for each organization:
      resolve TenantContext(kind=JOB)          (skip if it became unavailable)
      open THAT tenant database
      run attendance recalculation / report export
      close / release that tenant's resources
```

`run_per_tenant()` (in `resolver.py`) implements this loop. Each tenant gets
a fresh context, and an exception in tenant A is recorded but never
continues against tenant B (tested).

- **Google Sheets:** a report job exports *Tenant A database → Tenant A
  report*. It never aggregates A and B. Sheets authentication is unchanged
  in this phase; a later phase moves it to the service's runtime identity.
- **No cross-tenant API:** no repository function lists all tenants'
  employees or activity (tested). A platform-level aggregate would be a
  separately designed and authorized feature, ideally from anonymized
  statistics, not raw activity.
- Cloud Scheduler is not configured yet.

## 14. Platform administration — limits

ZaZa staff will need a platform admin interface: listing organizations,
suspending one, or checking a tenant database's status.
**`PLATFORM_SUPERADMIN` is not an organization role**, and it does **not**
mean "can read every employee's activity".
- Platform administration works on the control plane: organizations,
  directory and audit.
- Reading a tenant's activity data is not part of it.
- No platform admin model is implemented in this phase.

## 15. Support access principle

If ZaZa staff ever need to look inside a customer's data, access must be:
- **explicit**: a request tied to a ticket and a reason;
- **time-limited**: it expires;
- **audited**: in the control audit log, as a `PLATFORM` actor;
- **visible to the customer** where practical.

It is never silent and never a standing permission. Support impersonation
is **not** implemented.

## 16. Cloud SQL connection strategy (Phase 10D)

**Implemented in Phase 10D** (`tenancy/connections.py`, `cloudsql.py`; see
[CLOUD_SQL_PRODUCTION.md](CLOUD_SQL_PRODUCTION.md) §2–§6):
- lazy, bounded LRU cache of tenant pools (min 0, max 2; 8 pools per
  instance; idle close after 300 s, all configurable within hard limits);
- the Cloud SQL Unix socket and Secret Manager password files;
- a connection budget checked by `check-config --cloud-run`;
- runtime / migrator / reporting roles.

Per-tenant roles remain a later option. The original requirements:

- **Connection pools:**
  - created **lazily**, on first use of a tenant;
  - **small per-tenant pools** (1–2 connections);
  - a **bounded number of open pools** (LRU), with **idle eviction**;
  - **no pool per tenant ever seen**, which would leak without bound.
- **Total connections** must fit the Cloud SQL instance limit across all
  Cloud Run instances. Concurrency, max-instances and pool sizes are
  designed together, or a connection proxy/pooler is put in front.
- **Credentials** come from Secret Manager or IAM database authentication via
  the service's identity, not from the control database and not built into
  the image (see `deploy/gcp/README.md`).
- **Least privilege:**
  - one database role per purpose (application, migration, read-only
    reporting), as in the Windows deployment design;
  - **per-tenant roles if feasible**, so a credential for A cannot even
    connect to B.

## 17. Future enrollment (not implemented)

Phase 10F-B implemented the parts enrollment will build on: the device
credential route (`device_credential_routes`, domain-separated hash →
organization; a route is not authentication), the route lifecycle
(create, revoke, rotate) and the credential-routed SaaS sync API. See
[SAAS_AUTH.md](SAAS_AUTH.md). The enrollment endpoint itself is still
future work.

```
organization ADMIN creates a one-time enrollment code (short-lived, single use, stored hashed)
      → the employee's installer/agent submits the code once
      → server resolves the organization from the code
      → device registered in that tenant database
      → code consumed/expired
      → device receives its long-lived, rotatable zzd_ credential; the router index learns its organization
```

The design rules out:
- a permanent company-wide API key;
- a tenant secret embedded in the Windows installer;
- an organization chosen by the client.

## 18. Future billing / subscriptions (not implemented)

Billing will attach to `organizations` from a separate part of the control
plane (subscription, plan, seats, trial). It will **decide** an
organization's status; it will never be stored in tenant databases or
reachable from tenant code. No payment provider, pricing, seat or trial
enforcement exists yet.

## 19. Backup and restore implications

- **Backups:**
  - Cloud SQL backups are per instance. Per-tenant logical backups
    (`pg_dump` of one `zaza_t_…` database) allow restoring **one** customer
    without touching others.
  - The control database is backed up separately and is small.
- **Restoring a tenant** means restoring its database, checking its
  `schema_revision` against the head, then re-marking it `READY`. A restore
  must never overwrite another tenant's database: the name comes from the
  directory, not from the operator's memory.
- **Retention and deletion:** an organization that leaves can be exported
  and its database dropped as a unit. The control rows stay for audit.

## 20. Isolation threat model

| Threat | Mitigation |
|---|---|
| Missing tenant filter in a normal query | database-per-tenant: a tenant connection can't see other tenants' rows |
| Client sends another organization id / slug | the organization comes from the credential or membership; claimed ids are only compared; slugs are handles; TenantContext is unforgeable |
| Valid token of A used to reach B | router maps the token to A; the claim of B is refused; the token is also verified inside the routed tenant |
| Crafted database name / connection string | names generated server-side, strict pattern in code and database, connection details only from server config |
| Employee classified `ADMIN` gains SaaS rights | `employees.role` never maps to membership roles; only `organization_memberships` grants |
| Job for A runs against B after an error | each job iteration has its own context; failures stay with their tenant |
| Activity data leaks into the control plane | no activity tables or activity queries in the control code (tested); the control audit holds metadata only |
| Control and tenant schemas mixed in one database | cross-guards in both migration runners; separate version tables and chains |
| Tampering with the history of administrative changes | `control_audit_logs` is append-only (trigger); identifiers are immutable |
| Platform staff browsing customer activity | platform admin ≠ tenant data access; support access must be explicit, temporary and audited (§15) |
| Connection or pool exhaustion across many tenants | bounded, lazy, evicting pools (§16, Phase 10D) |

Still open before public deployment:
- the Cloud Run trusted-proxy, HTTPS/origin, dashboard-mounting,
  rate-limiting and preflight items in `deploy/gcp/README.md`;
- Cloud SQL itself;
- SaaS authentication;
- enrollment.

The privacy model is unchanged: no screenshots, screen recording, OCR,
keystrokes, clipboard, audio, video, browser history, URLs, search or page
content are collected (SECURITY.md §2.2).
